# H200 execution guide

GPU rental and competition submission are separate actions requiring the owner's
authorization. The commands below are prepared for the owner-provided machine;
none was executed on an H200 during Phase A.

## Container and source

Install/use the host's NVIDIA driver and NVIDIA Container Toolkit. Verify an H200
SXM with `nvidia-smi`; record driver, memory, power limit, clocks and other GPU
processes. Use an idle GPU. Do not assume the advertised model alone establishes
performance parity with the judge.

```bash
git clone --branch feat/muse-bf16-proj https://github.com/asifehmad/openkernel-challenge.git
cd openkernel-challenge
docker pull lmsysorg/sglang:dev-muse-spark-open
docker image inspect lmsysorg/sglang:dev-muse-spark-open --format '{{json .RepoDigests}}'
docker run --rm -it --gpus all --ipc=host \
  --mount type=bind,src="$PWD",dst=/work \
  --workdir /work lmsysorg/sglang:dev-muse-spark-open bash
# Inside the container:
bash scripts/setup.sh gpu
python scripts/verify_environment.py --require-h200 > benchmarks/results/environment.json
```

Record the image digest and rerun using `lmsysorg/sglang@sha256:<recorded-digest>`
for repeatability. The mutable tag is not an immutable environment. Never run
the CPU setup command inside this image: it installs CPU PyTorch. The GPU setup
now performs verification only: it installs nothing and preserves all image
packages, including NumPy, torch/Triton/SGLang.
Confirm the current official task names this image and its dependency versions.

The registry was reached directly during this update. The Linux/amd64 manifest
digest is `sha256:a0ae9cefecc0fb68e74a6f3b7f338eb80a53e3e6df4637ec2f024abc5fec07af`.
Its checksum-verified config declares CUDA 13.0.3; installed torch/Triton/SGLang
versions remain unverified. See [manifest evidence](container_manifest.json).
The layers total 23.9 GB compressed, so reserve substantially more space for
unpacking and caches (100 GB free is a practical starting allowance, not a
measured image requirement). This sandbox had 29 GB free and did not pull/unpack
or execute the image. Do not infer driver compatibility from package metadata;
the container and GPU smoke must actually start on the rented host.

The current cloud proxy blocks the website, installer and API. The following
commands require that access on the H200 host/container. No official CLI command
has been run here, so its current version and command-specific syntax must be
confirmed with the downloaded CLI's help. Do not install the unrelated PyPI okc.

For the owner's Hostinger VPS, use the complete staged
[installation and human-authentication guide](hostinger.md). This session has
no VPS connection; no CLI installation or login has been performed there.

## Exact local GPU session

Once the current task is reconciled and OFFICIAL_DIR set as above:

```bash
# Minimal first launch: one full-size QKV projection at M16, one candidate.
bash scripts/first_h200_session.sh benchmarks/results/smoke-default \
  --smoke-only --entry-point kernel_fn
# Same representative input shape, with the other native paths:
bash scripts/first_h200_session.sh benchmarks/results/smoke-single \
  --smoke-only --entry-point single_pass_kernel_fn
bash scripts/first_h200_session.sh benchmarks/results/smoke-gemv \
  --smoke-only --entry-point gemv_kernel_fn
# Only after smoke passes, run full correctness and measurements:
bash scripts/first_h200_session.sh benchmarks/results/h200-audit-001
```

The smoke stage imports the supplied SGLang baseline and candidate, checks eager
results and output retention, then exercises the exact external-event graph
timer on fresh normal, outlier and zero inputs. It reports no speedup. The
session script finds the actual task directory without assuming CLI nesting
and stops if task/reference/check/baseline hashes differ from the reviewed
snapshot. Reconcile real differences rather than bypassing that check.

This script stops on failure. It verifies H200/dependencies, runs full-dimension
local correctness against the supplied checker on two fresh seeds for each of
the default, single-pass and GEMV variants, runs SGLang A/A calibration, then
benchmarks all 30 shapes for each variant and writes JSON/CSV/Markdown reports.
It never uses official check quota or submits a leaderboard entry.

To run or retry candidates independently, use new directories:

```bash
for entry in kernel_fn single_pass_kernel_fn gemv_kernel_fn; do
  bash scripts/first_h200_session.sh "benchmarks/results/independent-$entry" \
    --entry-point "$entry" || echo "Failed: $entry (inspect its saved results)"
done
# Include only successfully completed run directories:
python scripts/summarize_candidates.py \
  benchmarks/results/independent-kernel_fn \
  benchmarks/results/independent-single_pass_kernel_fn \
  benchmarks/results/independent-gemv_kernel_fn \
  --output benchmarks/results/independent-selection.json
```

Each run retains a read-only source copy plus its exact task bundle. Selection
requires full GPU correctness on two seeds, fresh-input graph passes, successful
smoke, all 30 timings, A/A gates, matching source/task hashes and comparable runtime
and measurement settings. It records the best observed entry point and all
alternatives without modifying `kernel_fn`. Margins below 3% are marked
inconclusive (a heuristic, not a confidence interval). Repeat on fresh seeds;
compare only matching settings within each trial. No eligible GPU candidate
exists yet in this repository.

Each benchmark also performs A/A pairs before and after every shape. Raw
in-graph intervals are default; launch overhead is already excluded. To inspect
the experimental empty-event correction separately, use a new directory:

```bash
python benchmarks/benchmark.py --official-dir "$OFFICIAL_DIR" --aa-only \
  --correction empty --repeats 30 --aa-repeats 12 --warmup 20 \
  --output benchmarks/results/h200-aa-empty
```

Failed bias/noise/correction gates mean **no usable aggregate result**. Inspect
raw samples, idle GPU state and versions; do not silently relax gates to report
a gain. Empty correction is optional and not claimed to reproduce the private
judge. A/A itself cannot prove absolute timing accuracy. The external-event
graph code must execute successfully on the actual image before trusting it.

Repeat promising candidates with new seeds and result directories. All measured
baselines come from the supplied bundle's SGLang code. `torch_kernel_fn` is a
candidate-side control only. The reports rank score sensitivity to guide tuning.

## Profiling and experiments

Local score estimates alone do not establish a judge result. Do not time under
Nsight Compute: metric collection changes execution. First measure normally,
then profile the highest load-contribution shape in a separate diagnostic run:

```bash
ncu --set full --profile-from-start off --target-processes all \
  -o benchmarks/results/profile-pooler \
  python scripts/profile_kernel.py --official-dir "$OFFICIAL_DIR" \
  --layer pooler --m 16 --entry-point single_pass_kernel_fn
```

The profiling script brackets only the candidate graph replay with the CUDA
profiler start/stop range; JIT, warmup and reference validation are outside it.
The full metric set is expensive: narrow metrics using your installed
`ncu --help` when needed. This is a diagnostic run with no benchmark score.
Record registers/thread, static/dynamic shared bytes, achieved occupancy,
DRAM throughput, tensor-pipe utilization and spill/local-memory activity.
Hardware profiling may require host permissions; keep that separate from
correctness. Use `ncu --query-metrics` for names in the installed version.

Change one major parameter at a time, retain raw history and record the commit,
candidate SHA256 and seed in every result. Keep the last **GPU-correct** candidate
before promoting a dispatch change. Phase A does not yet provide one. Check all
30 shapes before claiming an aggregate gain, and ensure preparation stays below
the documented 300 seconds and complete official execution below 10 minutes.
Check current rules for a memory cap; no cap has been independently confirmed.

No script performs login, remote checks or submissions. A human must accept
terms with `okc login`. Do not enter credentials in Git or chat. The final
`okc submit` action and any `okc check` quota use each require explicit owner approval.
