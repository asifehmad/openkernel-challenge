## Architecture and library sources actually read

1. [NVIDIA CUTLASS: efficient GEMM](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/efficient_gemm.md), particularly split/sliced K and Hopper warp specialization. Producer warp groups issue TMA transfers; consumer groups execute tensor-core work with explicit stage barriers. Persistent cooperative kernels amortize prologues; ping-pong designs overlap different tiles' epilogues and MMA. Larger tiles improve reuse but increase accumulator registers, shared memory and occupancy pressure.
2. [NVIDIA CUTLASS Hopper collective-builder example](https://github.com/NVIDIA/cutlass/blob/main/examples/49_hopper_gemm_with_collective_builder/49_collective_builder.cu). Useful starting point for choosing SM90 schedules, tile layouts, stage counts and alignments. Hopper WGMMA variants may require `sm_90a`; verify compiler and library support in the pinned evaluation image before adopting them.
3. [Triton persistent-matmul tutorial](https://github.com/triton-lang/triton/blob/main/python/tutorials/09-persistent-matmul.py). Compares conventional, persistent and TMA kernels. Current upstream APIs are not necessarily the image's APIs. CLC and the two-CTA TMA mode in this tutorial require Blackwell; do not port those branches to H200. Hopper TMA/persistent experiments must use supported versions and capture-safe descriptor lifetimes.
4. [SGLang unquantized dispatch at the task's pinned commit](https://github.com/sgl-project/sglang/blob/a55ab7d5ae1bba59ac351e55026fe7f7644ecc5f/python/sglang/srt/layers/quantization/unquant.py). `_bf16_gemm_dispatch_impl` may use explicitly enabled split-K, Hopper GEMV or CuTe routes, then falls back to `F.linear`. The task's baseline describes cuBLAS on H200. Run the supplied baseline in the official image; do not silently substitute a modern SGLang install or plain PyTorch and label that result SGLang.

The NVIDIA [Hopper tuning guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html) and rendered Triton site were also requested but proxy-blocked. They remain follow-up reading; no claim here relies on having read their current rendered contents. The upstream source links above were accessible. Their `main` revisions are mutable; record exact revisions when adopting implementation details.

## Candidate strategy and bottlenecks

The current candidate is independently implemented. Its provisional dispatch is a Triton GEMV for M=1 BF16 projections, tensor-core split-K GEMM for other small BF16 batches, PyTorch GEMM for larger BF16 batches, an exact FP32-weight Triton reduction for small router batches, and a fused BF16 hi+lo router dot for larger batches. These are hypotheses awaiting GPU compilation, correctness and timing; they are not selected winners.

The task's advertised roofline uses 4.8 TB/s HBM bandwidth and 989 TFLOP/s dense BF16 compute. For each shape, the ideal lower bound is:

`max((N*K*weight_bytes + M*K*2 + M*N*output_bytes)/4.8e12, 2*M*N*K/989e12)` seconds.

This excludes launch and synchronization costs and assumes ideal use of the machine. In particular the BF16 throughput number is not a performance model for an FP32 SIMT router. Effective bandwidth computed from logical bytes is a diagnostic, not a measurement of physical DRAM traffic; use Nsight counters for the latter.

| Technique | Why investigate | Main constraint / required evidence |
|---|---|---|
| Specialized GEMV and cooperative reduction | Avoid padded tensor-core work at M=1; stream contiguous K elements, reuse activation fragments | FP32 accumulation, register footprint, enough independent CTAs and reduction cost; measure full weight stream with cold L2 |
| Small-M tensor-core GEMM | Reuse each streamed weight across M=8/16/32 activations | Padding, tile occupancy and masks; compare with GEMV and cuBLAS, including nearby M |
| Split K | Increase parallelism when output tile count is too small | FP32 partial storage, extra launch/reduction and rounding can erase gains; fully initialize scratch on every call |
| Persistent kernels | Amortize CTA prologue and balance work across SMs | Small grids can underfill the device; weight rereads, tail balance and runtime compatibility |
| TMA and warp specialization | Overlap global-to-shared traffic with WGMMA and reduce address-generation overhead | Alignment, descriptor lifetime, stage barriers, shared-memory budget; H200-supported features only |
| Vectorized/coalesced reads | Improve useful bytes per memory transaction | Preserve original BF16 bits; measure L2/HBM transaction counters and tail masking |
| ILP and scheduling | Keep independent loads and arithmetic in flight | Register spills/local-memory traffic; more stages are not automatically faster |
| Shared-memory/layout tuning | Reuse activations and feed tensor cores efficiently | Bank conflicts and per-SM residency; query actual resources rather than aiming at occupancy alone |
| Weight transpose or packing in `prepare` | Remove repeated layout work; improve streaming and tensor-core access | Preparation <=300 s in snapshot; memory cap still unknown; original weights and all representations count |
| Lossless BF16 compression | Reduce cold weight traffic for small M | Bit-exact reconstruction for every value, escape cases and arbitrary weights; codec overhead and extra metadata may dominate |
| FP32 router decomposition | BF16 hi+lo is expressly allowed by the snapshot; combine two dot products in FP32 | BF16-only weights and TF32 shortcuts are not acceptable substitutes; probe/outlier error checks apply |
| Per-shape/library dispatch | Different dimensions favor different backends | Dispatch only on public metadata; avoid input values/seeds, validate nearby shapes and graph capture |
| CUDA graphs | Match the challenge's execution mode and remove eager Python overhead | Fresh inputs, output retention, graph replay, no timed host sync; capture all required computation |

## Published results: context, not our measurements

[NathenFernandes/muse-bf16-proj](https://github.com/NathenFernandes/muse-bf16-proj), revision `86aff75e6aca72511bf9b41b6dc190bf1e763373`, reports a judged 1.5186× result and nine passed tests. Its README describes small-M lossless packing, Hopper WGMMA/TMA and selected cuBLASLt routes. License: MIT. We read documentation and did not copy its implementation.

[alygg77/okc-muse-spark-kernels](https://github.com/alygg77/okc-muse-spark-kernels), revision `6cae49a639ee6d14b929a5fd4a63c627f96d7dc0`, reports 1.5502× and rank 75 on 2026-10-29. Its [negative results](https://github.com/alygg77/okc-muse-spark-kernels/blob/6cae49a639ee6d14b929a5fd4a63c627f96d7dc0/docs/NEGATIVE_RESULTS.md) report split-K at QKV M256 losing 3.3–4.6 µs from partial-result traffic, and lossless decode at larger M losing through arithmetic contention. These are measurements on their implementations, not facts about this candidate. Their documented variation across repeated judge runs also argues for repeated paired comparisons and a noise threshold before retaining changes. License: Apache-2.0 with attributed MIT components. No implementation was copied.

The Xuefeng snapshot repository carries Apache-2.0; the lilac repository had no standalone LICENSE observed. Challenge terms are reported by those authors to license submissions under Apache-2.0, but current official terms still need direct review. Preserve upstream provenance and licenses for any vendored material. Do not infer that public visibility alone permits code reuse.

The user's 4.83 ms baseline and 2.93 ms target remain requested targets rather than live-verified figures. The mirrored API's historical `sglang_us=4830.8` corroborates the rounded baseline but does not measure this environment. Public competitor ranking claims are insufficient to establish today's leading submission.
